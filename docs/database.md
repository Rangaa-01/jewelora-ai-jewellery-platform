# Database

PostgreSQL 14+ (17 in Docker). Schema is owned by Alembic (`backend/alembic`). Never edit a
production schema by hand: write a migration, review the autogenerated diff, run
`alembic upgrade head` as a release step (the Docker stack does this in the `migrate`
service before the API starts).

```bash
cd backend
.venv/bin/alembic revision --autogenerate -m "describe change"
.venv/bin/alembic upgrade head
.venv/bin/alembic check        # fails if models and migrations drift (CI runs this)
.venv/bin/alembic downgrade -1
```

Extensions: `pgcrypto`, `pg_trgm` (fuzzy product search), `citext` (case-insensitive email).

## Entity overview

```
users ──< user_roles >── roles            refresh_tokens, otp_codes ──> users
users ──1 customers ──< wishlists ──< wishlist_items ──> products / saved_looks
                   ├─< saved_looks ──< saved_look_items ──> products, product_variants, product_sizes
                   ├─< customer_photos ──< tryon_sessions ──< tryon_results
                   ├─< carts ──< cart_items          ├─< orders ──< order_items, payments
                   ├─< appointments ──> stores        └─< enquiries ──> products
product_categories (tree) ──< products ──< product_variants, product_images (──1 product_embeddings),
                                            product_tryon_assets, product_3d_assets, product_sizes,
                                            product_set_items (self-reference), product_collections >── collections
metal_rates · stylist_requests · analytics_events (append-only)
```

Key rules:

- UUID primary keys everywhere except `roles`. `created_at`/`updated_at` via server defaults.
- Soft delete with `is_active` for products/categories/collections/stores/users;
  hard delete of a product is refused once it has been ordered.
- Order items snapshot SKU, name, price and image so history never changes.
- Variants are explicit rows: a metal/stone combination exists only if the shop configured it.
- `product_tryon_assets.anchors` (JSONB) holds normalised anchor points; see `docs/ai-tryon.md`.
- `customer_photos` are private: `storage_key` under `private/`, `expires_at` enforced by the
  cleanup job, `landmarks` cached JSON so re-runs skip detection.
- `analytics_events` is the source for the admin analytics; it is never updated, only appended.

Indexes: FKs, `products(is_active, category_id)`, `products(jewellery_type)`, trigram GIN on
`products.name`, GIN on `products.tags`, `analytics_events(event_type, occurred_at)`,
`analytics_events(product_id, occurred_at)`, `appointments(store_id, starts_at)`,
`orders(status, created_at)`.

## Seed data

`make seed` loads `database/seeds/catalogue.json` and generates assets. It is idempotent
(skips existing SKUs/slugs) and refuses to run with `APP_ENV=production`.

## Backups

Use `pg_dump --format=custom` on a schedule and store object-storage snapshots alongside;
`tryon_results`/`customer_photos` reference storage keys, so restore both together.
